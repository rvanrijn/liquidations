Cascade Radar

A live screen that shows, in real time, exactly what the liqhunt/krakenbot strategy perceives — liquidations raining onto the price as they’re pulled toward the magnet levels — without ever placing a trade.

READ-ONLY · NO TRADES · NO DB Binance public feeds FastAPI + WebSocket D3 / SVG

What it is

The liqhunt strategy hunts liquidation cascades: when leveraged positions get force-closed, the forced orders push price toward clusters of other stops (“magnets”), and that chain reaction is a tradeable 0.5% move. The trading bot watches Open Interest, CVD, funding and the liquidation feed to decide when to act.

The Cascade Radar is the bot’s eyes, on a screen. It re-runs the bot’s exact perception logic locally and visualizes it — the liquidation stream, the magnet levels, the order-flow gauges, and the engine’s live verdict. It’s for watching a session, not for executing: it has no order code and writes to no database.

How it works

One read-only pipeline, four stages — public market data in, a picture out:

1 · Feeds
Binance (public)
Liquidation forceOrder stream + price, OI, CVD, funding. No keys, no account.
→
2 · Engine
SignalEngine.evaluate()
The bot’s real decision code, run read-only. Emits a signal — or a reason it didn’t.
→
3 · Transport
WebSocket /ws
Per-event liq blips + a ~2 Hz state snapshot.
→
4 · View
D3 radar
Browser renders the field, gauges and verdict; buffers its own history.

The engine and feed code are the production strategy’s own modules, reused unchanged. The radar adds only a read-only loop, the transport, and the view — and a guard test fails the build if any trading or database-write call ever sneaks into the radar package.

Reading the screen

Red blips — longs liquidated

A long position was force-sold. Dot size ∝ USD liquidated; it pulses, then drifts left and fades over the 5-minute window.

Green blips — shorts liquidated

A short got squeezed out (force-bought). Big events (>$250K) drop an expanding shockwave ring.

Magnet bands

Horizontal glowing zones where stop clusters sit (labelled with price & $). Brighter = more liquidity. Price tends to get pulled toward the bigger side.

Price trace + grid

The live price line, centered, with the “now” dot on the right. The whole field scrolls left as time passes (x = time, y = price).

Quality gauge

The engine’s 0–1 setup score, live every cycle (blue→amber→green). Built from OI depth, imbalance, funding alignment, volatility, velocity & taker flow.

Imbalance & rail

Long-vs-short stop $ split, plus OI Δ, OI velocity, CVD, funding, taker ratio, and feed-health dots (green = connected).

Bottom strip = cascade intensity: net liquidation $ per 5-second bucket, red above / green below the midline — the “storm” building or fading.

The engine’s verdict

STANDBY · reason

Most of the time the engine isn’t armed. The banner shows the live reason — e.g. “No sweep toward LONG magnet” or “Imbalance insufficient (1.18× < 1.3×)” — updated every cycle. The quality gauge still moves so you can see a setup building.

ARMED LONG → target · stop

When every gate passes — imbalance, OI cascade, velocity and a validated sweep — the banner flips, glowing amber, and shows direction, target and stop. This is the moment the bot would act on.

Run it

# from the radar repo root
uvicorn src.radar.server:app --host 127.0.0.1 --port 8800
# then open  →  http://127.0.0.1:8800

A single local process. It needs no API keys, no account, and no VPS — just outbound access to Binance’s public endpoints.

Dev / test mode

The bot skips its worst-win-rate day (Saturday). To exercise the full pipeline on any day, launch with the dev toggle — it relaxes the day filter in the radar process only (the real bot is untouched) and shows a pulsing ⚙ DEV · day filter off badge so you always know you’re in test mode:

RADAR_IGNORE_DAY_FILTER=1 uvicorn src.radar.server:app --port 8800

Guarantees

  • Read-only. Imports no trader/executor; opens no DB write handle — enforced by an automated guard test.
  • No shared-state risk. Derives everything from live feeds; never writes the bot’s database or JSON.
  • Faithful. Uses the production engine & feed modules unchanged, so the picture matches what the bot sees.
  • Self-contained. Pure logic is isolated and unit-tested; the live loop degrades gracefully when optional feeds are absent.
